# 面试锦囊

适配简历关键词：
- Spring Boot
- Spring AI
- PostgreSQL / PGVector
- Redis
- Docker
- React
- MCP Protocol
- DDD
- AI Agent 编排平台

项目主线：
- 动态配置 Agent
- RAG 知识库
- 标准化执行流程
- 简历评估与模拟面试
- 文档知识助手
- 内容自动化
- 审计监控与工作台大盘

这份稿子的目标不是把项目讲大，而是把你已经做出来的能力讲清楚，讲出工程价值、技术判断和设计理由。

## 1. 怎么开场讲项目，让面试官眼前一亮

### 推荐开场

你可以直接这样讲：

> 我最近做的核心项目是一个企业级 AI 智能体编排平台，技术栈是 Spring Boot、Spring AI、PostgreSQL PGVector、Redis、React 和 MCP Protocol。  
> 这个项目我不是把它做成一个单点聊天应用，而是围绕三件事搭平台能力：第一是动态配置 Agent，第二是企业私有 RAG 知识库，第三是标准化执行流程。  
> 在架构上我采用了 DDD，把业务场景、执行引擎、配置装配和基础设施分开。  
> 在执行层我设计了统一的四步流程：分析、执行、质检、总结，重点解决大模型长流程任务不稳定、结果不可控的问题。  
> 在知识层我基于 PGVector 做文档切片、向量化和检索，配合 Spring AI 的 ChatMemory 和 Redis 管理会话状态，兼顾了多轮对话质量和 Token 成本。  
> 最后这个平台不只是底层框架，我把它落到了简历评估、模拟面试、文档知识问答和内容自动化这些具体场景里。

### 这段开场为什么有效

因为它同时把 4 个核心点讲出来了：
- 你做的是平台，不是单点 demo
- 你负责的是后端架构和执行引擎，不只是写 prompt
- 你能讲清楚 Agent、RAG、状态管理、执行治理
- 你能把底层能力落到具体业务场景

### 开场后顺势接一句

> 这个项目如果往下展开，我觉得最值得讲的是三块：执行流引擎、RAG 和记忆架构、以及为什么要做动态装配和全链路流式交互。

这句话能把面试官自然带到你擅长的区域。

## 2. 根据简历内容推断面试问题链 + 标准回答

下面按高频追问顺序整理。

### 2.1 你这个平台到底解决什么问题

标准回答：

> 它解决的是企业里 AI 能力落地时最常见的三个问题：  
> 第一，怎么让 Agent 不是写死在代码里，而是能通过配置快速组装；  
> 第二，怎么让模型回答能结合企业私有知识，而不是只做裸调用；  
> 第三，怎么让复杂任务的执行过程可控、可恢复、可观测。  
>  
> 所以我做的不是一个聊天机器人，而是一套 AI 任务编排平台。上层可以快速接不同业务场景，下层统一复用动态装配、RAG 检索和标准化执行引擎。

### 2.2 为什么要做“动态配置 Agent”

标准回答：

> 因为如果 Agent 的角色、工具、知识库都写死在代码里，后续新增场景的成本会很高。  
> 我做了一个 Armory 模块，把 AI 角色、MCP 工具、RAG 知识库这些能力的创建逻辑统一收口，用策略模式加工厂模式按配置动态装配。  
> 这样新加一个场景时，不用每次都改一套硬编码初始化逻辑，而是通过配置和装配链快速复用已有能力。

### 2.3 你说的 Armory 是什么，为什么要单独做

标准回答：

> Armory 本质上就是智能体能力装配中心。  
> 它负责统一管理三类资源：  
> 1. 模型角色和客户端  
> 2. MCP 工具  
> 3. RAG 知识库和 Advisor  
>  
> 我单独做这个模块，是为了把“业务执行”和“能力创建”拆开。  
> 业务层只关心这次任务要什么能力，Armory 负责把这些能力组合出来。  
> 这样平台扩展性会更好，执行链也不会和底层配置强耦合。

### 2.4 你提到并发优化，具体优化了什么

标准回答：

> 动态装配有一个天然问题，就是角色、工具、知识库如果串行初始化，Agent 启动会比较慢。  
> 所以我在装配层用了自定义线程池加 CompletableFuture，把多维配置的加载并发化。  
> 例如模型客户端、MCP 工具和 RAG 相关能力可以异步准备，最后再统一聚合。  
> 这样做的收益主要体现在初始化耗时下降，也减少了单条长链路里不必要的等待。

### 2.5 你的标准化执行流程为什么是“分析 -> 执行 -> 质检 -> 总结”

标准回答：

> 因为复杂任务最怕两件事：一步出结论和结果不可控。  
> 所以我把执行过程拆成四步：  
> 1. 分析：明确任务目标、约束和拆解策略  
> 2. 执行：生成核心结果  
> 3. 质检：做一致性校验、自我反思和必要重试  
> 4. 总结：把最终结果整理成可消费输出  
>  
> 这样做的价值是把“产出”和“纠偏”拆开。尤其是质检节点，我引入了大模型自我反思机制，不是只看一次生成结果，而是再做交叉验证，提升复杂任务的稳定性。

### 2.6 你说的“自我反思机制”具体怎么理解

标准回答：

> 自我反思不是让模型泛泛地再想一遍，而是给它一个明确的复核职责。  
> 执行节点负责产出结果，质检节点再从目标一致性、上下文贴合度、结果完整性这些角度检查前一步输出。  
> 如果发现明显偏离，就走动态重试或降级。  
>  
> 这个设计本质上是把单次生成变成“生成 + 校验”的闭环，它比只堆 prompt 更有工程可控性。

### 2.7 你们 RAG 是怎么做的

标准回答：

> 我们的 RAG 链路比较标准，但我比较关注工程边界。  
> 整体流程是：文档上传 -> 解析 -> 切片 -> 向量化 -> PGVector 存储 -> 相似度检索 -> 构造上下文 -> 模型生成。  
>  
> 关键点有三个：  
> 1. 文档切片和 metadata 设计要稳定，后续才能支持过滤和扩展  
> 2. 不同业务场景的向量空间要隔离，比如简历和文档助手不能混用  
> 3. 检索不是目的，最终要为业务回答服务，所以我会把 retrieval scope、命中片段和最终上下文都保留下来，方便审计和定位问题。

### 2.8 为什么选 PostgreSQL + PGVector

标准回答：

> 这个选择主要是工程权衡。  
> 因为项目本身已经有关系型数据模型，知识空间、文档、任务、会话这些元数据天然适合放在数据库里。  
> PGVector 能让我们在同一套 PostgreSQL 里同时管理结构化数据和向量检索，开发和运维成本比较低。  
> 对第一版企业内部场景来说，这个方案足够稳，也方便后续按业务做 metadata 过滤和多表隔离。

### 2.9 你怎么解决长对话上下文膨胀问题

标准回答：

> 我没有简单地无限叠加历史消息，而是做了“窗口记忆 + 状态外置”。  
> 在模型侧我使用 Spring AI 的 ChatMemory 控制窗口记忆，只保留当前任务真正需要的上下文。  
> 在系统侧我把会话状态、近期对话和热点问答放到 Redis 管理。  
> 这样多轮交互时，模型不需要吃下全部历史文本，既降低了 Token 成本，也减少了长上下文导致的噪声。

### 2.10 Redis 在这里主要承担什么职责

标准回答：

> Redis 在这个项目里不是主存储，而是状态和热点数据层。  
> 我主要用它做三件事：  
> 1. Agent 会话状态管理  
> 2. 近期对话和上下文恢复  
> 3. 热点问答缓存  
>  
> 它的价值在于把高频、短生命周期的数据从主业务存储里拆出来，提升多轮交互效率，也方便页面恢复。

### 2.11 MCP Protocol 在项目里怎么用

标准回答：

> MCP 我把它看成模型访问外部能力的标准化协议层。  
> 在平台里我没有把工具调用做成一堆零散的 SDK 直连，而是把 MCP 工具纳入 Armory 的统一装配逻辑。  
> 这样 Agent 在运行时能按配置挂载工具能力，业务层不需要关心底层工具实现细节。  
> 这也是平台化设计的一部分。

### 2.12 SSE 为什么要做，为什么不用普通 HTTP

标准回答：

> 因为 AI 长任务很容易超过普通 HTTP 请求的用户心理等待阈值，甚至真实超时。  
> 所以我在服务端用 ResponseBodyEmitter 做了 SSE 单向长连接，把分析过程、工具调用日志和最终结果流式推到前端。  
>  
> 这样做有两个收益：  
> 1. 用户能看到过程，不会觉得系统卡死  
> 2. 后端的多步执行链可以被前端实时消费，而不是等最后一次性返回  
>  
> 对 Agent 产品来说，这种交互体验比单次请求返回更贴近真实使用场景。

### 2.13 你的前端为什么也值得讲

标准回答：

> 因为这个项目不是只有后端引擎，前端是把 Agent 过程可视化的重要一层。  
> 我这里不是做一个普通表单页，而是结合 SSE、页面恢复、任务详情、审计抽屉，把执行过程真正展示出来。  
> 特别是任务恢复这块，如果切页面回来就丢状态，平台体验会很差，所以我后面专门补了 active / recent 恢复接口和前端 restore 逻辑。

### 2.14 你们项目落地到了哪些业务场景

标准回答：

> 当前已经落地了 4 类场景：  
> 1. 简历评估  
> 2. 模拟面试  
> 3. 文档知识助手  
> 4. 内容自动化  
>  
> 这几个场景背后的共同点是都能复用平台底层能力，但执行模式并不完全一样。  
> 我们没有强行把所有问题都塞进一个通用 Agent，而是按场景选择更合适的执行方式。

### 2.15 那这些场景分别怎么跑

标准回答：

> 我们现在有三类执行方式：  
> 1. 单次 RAG + LLM：适合文档问答、摘要这类目标明确的任务  
> 2. 固定工作流：适合内容自动化这种节点稳定的流程  
> 3. 四步结构化执行：适合简历评估、模拟面试答题这种需要分析、复核和总结的任务  
>  
> 这样做比一个大而泛的 Agent 更稳定，也更利于调试和观测。

### 2.16 如果问到 Prompt 结构，怎么答

标准回答：

> Prompt 我一般按三层组织：  
> 1. 角色层：当前节点扮演什么角色  
> 2. 任务层：这一轮具体要输出什么、不能输出什么  
> 3. 上下文层：用户输入、检索结果、历史状态和前一步输出  
>  
> 这样做的好处是模板更稳定，也方便分步骤观察问题。  
> 比如分析节点更关注目标拆解，质检节点更关注一致性和真实性，总结节点更关注可读性和结构化输出。

### 2.17 如果问“为什么不用一个大 Agent 全做”

标准回答：

> 因为不同任务的确定性要求不一样。  
> 单次问答、固定流程、多步评估，这三类任务的复杂度、时延和治理方式完全不同。  
> 如果都塞进一个大 Agent，短期看统一，长期会在耗时、调试、审计和回归测试上全部变重。  
> 我做的平台化思路是统一底层能力，但不强行统一所有任务形态。

## 3. 开发难点和感悟

这是回答“你最近开发的难点是什么”的高质量版本。

### 推荐回答

> 我觉得这个项目最大的难点，不是某一个接口，而是怎么把 AI 调用真正纳入后端工程体系。  
>  
> 第一类难点是执行稳定性。  
> 长流程任务如果只做一次生成，结果波动会很大，所以我后来专门做了“分析 -> 执行 -> 质检 -> 总结”的四步引擎，把产出和纠偏拆开。  
>  
> 第二类难点是平台抽象。  
> 业务场景很多，但底层能力又有共性。我需要在“能复用”和“不过度抽象”之间找平衡，所以做了动态装配中心 Armory，把 Agent 角色、MCP 工具和 RAG 能力统一管理，但又没有强行把所有场景做成同一种执行模式。  
>  
> 第三类难点是上下文和状态管理。  
> 企业知识问答和模拟面试都不是单轮任务，既要保证上下文连续，又要控制 Token 成本，所以我用 ChatMemory 做窗口记忆，用 Redis 做状态和近期对话托管。  
>  
> 第四类难点是用户体验。  
> AI 任务天然会慢，如果只有最后一个结果返回，用户感知会很差，所以我用 SSE 把中间过程流式输出，让前端能实时展示执行过程。  
>  
> 这件事带给我的最大感悟是：AI 工程真正难的不是“调通模型”，而是把模型调用做成可维护、可恢复、可观测、可扩展的系统。

### 可以再补一句

> 我现在会更警惕两件事：  
> 第一，不要为了统一而牺牲场景边界；  
> 第二，不要只做 happy path，恢复、超时、降级、审计这些问题要尽早补。

## 4. 如果要上线，你觉得还有哪些工程功能没有做

这部分最能体现工程思维，不要泛泛而谈，直接按平台视角回答。

### 推荐回答

> 如果这个平台要正式上线，我觉得当前最需要补的不是“再多加几个场景”，而是把现有能力补到可运营、可治理、可控成本。  
> 我会优先补下面几块。

### 4.1 账号体系和多租户隔离

- 现在更偏单环境、单团队使用
- 真上线要有用户、组织、角色、权限
- 知识空间、任务、审计数据要按租户隔离

可直接回答：

> 现在平台能力已经有了，但上线必须补身份体系和多租户隔离，否则恢复接口、知识库接口和审计接口都会有越权风险。

### 4.2 异步任务调度体系

- 现在很多长任务还是应用内编排
- 上线后要补队列、重试、取消、死信、幂等
- 不能完全依赖单机线程池承载长链路

可直接回答：

> 现在的长任务更像应用内工作流，如果上线，我会把关键任务切到可靠异步调度体系里，不让 HTTP 链路直接承载整个任务生命周期。

### 4.3 模型路由和降级治理

- 不同步骤应该支持不同模型
- 要有配额监控、超时治理、限流、熔断、fallback
- client 与 model 的映射要更配置化

可直接回答：

> 当前已经有 client 和 model 的分层，但如果上线，还要补模型路由、配额治理和降级策略，否则一旦某个模型限流或超时，业务会直接受影响。

### 4.4 检索质量治理

- 当前已有基础 RAG
- 还可以继续补 rerank、多路召回、召回评估、命中质量分析
- 不应只盯最终答案

可直接回答：

> 现在的重点是把基础 RAG 链路跑稳了，如果上线，我会继续补重排、召回评估和命中质量分析，让检索质量可以量化优化。

### 4.5 更完整的可观测和告警

- 当前已有审计监控中心和工作台大盘
- 还缺真正的告警、异常聚合、成本看板、SLO
- 需要更系统的 trace 和事件关联

可直接回答：

> 现在已经能做执行详情和指标查看，但上线还要进一步补告警、成本分析、异常聚合和慢任务监控，这样问题才能真正被定位和治理。

### 4.6 安全和合规能力

- Prompt 注入防护
- 文件上传安全
- 敏感信息脱敏
- 密钥托管
- 输出审查

可直接回答：

> AI 平台上线不能只看功能，文件内容安全、模型输入输出安全、密钥管理和审计留痕都必须补齐。

### 4.7 自动化测试和交付体系

- 默认自动化测试集已经可以跑
- 还需要继续补 E2E、契约测试、回归链路
- 手工外部依赖测试应和默认测试分离

可直接回答：

> 我会把默认自动化测试、外部依赖测试和上线前回归分层管理，避免把所有测试混成一锅，这样 CI 才真正有意义。

## 最后收口

最后面试时，你不要把自己讲成“我做了一个很炫的大模型平台”，而是讲成：

> 我是站在 Java 后端工程的视角，把 AI 能力做成了一套可复用的企业级编排平台。  
> 我最有价值的部分不是调了多少模型，而是把动态装配、RAG、执行引擎、会话状态、流式交互和工程治理收住了。

这句话最稳，也最贴合你现在这份简历。
