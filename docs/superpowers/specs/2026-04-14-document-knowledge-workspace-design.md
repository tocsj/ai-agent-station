# 文档知识助手第一版设计

## 1. 目标

在现有 AI Agent Station 项目基础上，落地第一版 `Document Knowledge Workspace`，形成一条可演示、可扩展、可面试表达的文档知识工作台主链路。

第一版目标不是做泛聊天，也不是做连续 agent 对话，而是围绕文档知识空间提供稳定的 RAG 问答入口，并补充两个显式触发的可选能力：

1. 文档问答
2. 文档摘要
3. 生成追问
4. 生成测验

其中：

- 默认主流程是 `用户提问 -> Workspace 检索 -> LLM 回复`
- `生成追问` 和 `生成测验` 仅在用户点击时触发，不自动混入默认问答流程

## 2. 产品边界

### 2.1 第一版包含

1. 创建文档知识空间
2. 向同一个知识空间上传多个文档
3. 支持文件格式：
   - PDF
   - DOCX
   - TXT
   - Markdown
4. 文档解析、切分、向量化、入库
5. 基于当前 Workspace 的默认问答
6. 可切换检索范围：
   - 全部文档
   - 单个文档
7. 显式触发的辅助任务：
   - 文档摘要
   - 生成追问
   - 生成测验
8. 前端展示基础检索过程

### 2.2 第一版不做

1. 文档对比
2. 多文档组合筛选
3. 多路召回正式实现
4. 重排正式实现
5. 重型四步 Agent 默认问答链路
6. 自动连续追问
7. 与模拟面试合并的长会话流程

## 3. 产品定位

该页面是 `Document Knowledge Workspace`，不是聊天页。

它的定位是：

- 文档工作台
- 知识检索台
- AI 分析台

默认模式永远是问答，摘要/追问/测验是任务模式切换，不改变 Workspace 本质。

## 4. 页面设计

### 4.1 页面结构

采用三栏布局：

1. 左侧：Workspace 与文档区
2. 中间：任务与结果区
3. 右侧：检索过程与上下文区

### 4.2 顶部栏

展示：

- 页面标题：文档知识助手
- 当前 Workspace 名称
- 文档数量
- 当前检索范围
- 当前任务状态
- 新建 Workspace
- 上传文档

### 4.3 左侧栏

#### Workspace 卡片

展示：

- Workspace 名称
- 描述
- 文档总数
- 最近更新时间

操作：

- 新建空间
- 切换空间
- 重命名（可后补）

#### 上传区

展示：

- 上传按钮
- 支持格式：PDF / DOCX / TXT / Markdown
- 处理状态提示

状态流转：

- 上传中
- 解析中
- 切分中
- 入库中
- 已完成
- 失败

#### 文档列表

每个文档项展示：

- 文件名
- 文件类型
- 处理状态
- chunk 数
- 上传时间

支持切换：

- 全部文档
- 单个文档

### 4.4 中间主工作区

顶部任务模式切换：

- 问答
- 摘要
- 生成追问
- 生成测验

默认选中问答。

#### 问答模式

输入：

- 问题输入框
- 示例问题
- 发送按钮

输出：

- Markdown 回答
- 命中文档来源
- 当前检索范围

#### 摘要模式

输入：

- 摘要类型选择：
  - 摘要概览
  - 结构化摘要
  - 风险与待办

输出：

- 核心摘要
- 关键要点
- 风险点
- 待确认项

#### 生成追问模式

输入：

- 追问视角：
  - 技术评审
  - 业务理解
  - 项目推进
  - 面试准备

输出：

- 3 到 5 个高质量追问问题
- 每个问题可复制
- 每个问题可回填到问答框

#### 生成测验模式

输入：

- 题目数量：3 / 5 / 10
- 题型：简答题 / 选择题 / 混合

输出：

- 题目
- 可选参考答案
- 可选命中文档依据

### 4.5 右侧栏

用于展示检索过程和上下文。

展示内容：

1. Query 改写
2. 检索范围
3. 召回结果
4. 最终上下文
5. 运行状态

这部分第一版允许先做基础版展示，不要求一步到位完整可观测平台。

## 5. 架构设计

### 5.1 分层落点

沿用现有项目风格，不新起 MVC 三层。

#### app

负责：

- 文档工作流服务
- 上传、解析、切分、入库
- 文档问答/摘要/追问/测验编排

#### domain

负责：

- 文档空间实体
- 文档任务请求/响应实体
- 检索结果模型
- 可扩展的检索语义对象

#### trigger

负责：

- HTTP 接口
- SSE 输出
- 前端交互协议适配

### 5.2 运行时策略

第一版按任务复杂度分层：

#### 默认问答

采用：

- 单次 LLM
- Workspace 内向量召回
- RAG 返回

#### 摘要 / 追问 / 测验

也采用：

- 单次 LLM
- Workspace 内向量召回
- 按任务模式拼接 Prompt

第一版不默认走四步 Agent 链路。

原因：

1. 文档助手第一版重点是 Workspace 产品化
2. 问答/摘要/追问/测验都属于中低复杂度任务
3. 先把默认路径做稳，比一开始引入复杂编排更重要

### 5.3 与现有 Resume 场景的关系

复用现有能力：

- Tika 文档解析
- TokenTextSplitter
- PGVector
- RagAnswerAdvisor 思路
- SSE 输出
- 统一错误码/容错层

但产品边界保持区分：

- Resume 场景：围绕候选人知识空间
- Document 场景：围绕通用文档知识空间

## 6. 数据设计

### 6.1 复用方向

按蓝图复用以下三张业务表思路：

1. `ai_knowledge_space`
2. `ai_knowledge_document`
3. `ai_knowledge_chunk`

第一版将 `space_type=document` 真正用起来。

### 6.2 第一版最小语义

#### ai_knowledge_space

核心字段：

- `space_id`
- `space_name`
- `space_type=document`
- `description`
- `status`

#### ai_knowledge_document

核心字段：

- `doc_id`
- `space_id`
- `file_name`
- `file_type`
- `file_size`
- `parse_status`
- `chunk_count`
- `vector_status`

#### ai_knowledge_chunk

核心字段：

- `chunk_id`
- `doc_id`
- `space_id`
- `chunk_index`
- `chunk_text`
- `metadata_json`

### 6.3 向量表策略

Document 场景新建独立向量表，不与 Resume 向量表混用。

原因：

1. 避免与简历场景 metadata 混杂
2. 便于前端按 Workspace / docId 检索过滤
3. 后续更容易扩多路召回与重排

metadata 建议至少包含：

- `spaceId`
- `docId`
- `fileName`
- `chunkIndex`
- `docType=document`
- `knowledge=document_knowledge_space`

## 7. 检索边界

### 7.1 默认检索

默认只在当前 Workspace 内检索。

### 7.2 可选检索范围

前端可选：

1. 全部文档
2. 单个文档

第一版不支持多文档组合过滤。

### 7.3 检索返回

第一版建议至少保留以下可展示信息：

- 原始问题
- 改写后问题（可选）
- 命中文档名
- 命中 chunk 片段
- 最终拼接上下文

## 8. 接口设计

### 8.1 建议接口

1. `POST /api/v1/document/workspace/create`
2. `POST /api/v1/document/upload`
3. `GET /api/v1/document/workspace/{workspaceId}`
4. `POST /api/v1/document/ask/stream`
5. `POST /api/v1/document/summary`
6. `POST /api/v1/document/followup`
7. `POST /api/v1/document/quiz`

### 8.2 主接口语义

#### workspace/create

创建一个文档知识空间。

#### document/upload

上传文件并归属到某个 Workspace。

#### ask/stream

默认主流程接口：

- 用户问题
- 指定 Workspace
- 可选指定 docId
- 流式返回问答结果

#### summary / followup / quiz

显式点击触发的辅助任务。

不是默认对话链的一部分。

## 9. 前端交互约束

1. 若没有 Workspace，页面显示空状态，引导先创建 Workspace
2. 上传文档后自动刷新文档列表
3. 默认检索范围为全部文档
4. 切到单文档后，右侧检索范围同步更新
5. 问答是主入口
6. 追问和测验只有显式点击时才触发
7. 页面视觉应强调文件、检索、上下文、结果，而不是人格化聊天

## 10. 错误处理

第一版接入现有统一容错层，至少覆盖：

1. 文件格式非法
2. 文件过大
3. 文档解析失败
4. 向量入库失败
5. 检索失败
6. LLM 超时/重试/降级
7. SSE 断流保护

前端需能识别：

- 普通失败
- 可重试错误
- 已降级返回

## 11. 验收标准

1. 能创建 Workspace
2. 能向同一 Workspace 上传多个文档
3. 支持 PDF / DOCX / TXT / Markdown
4. 上传后能完成解析、切分、向量化
5. 能在 Workspace 内做默认问答
6. 能切换为单文档检索
7. 能显式生成追问
8. 能显式生成测验
9. 前端能看到基础检索过程
10. 整体实现不破坏现有 Resume/Interview 主链路

## 12. 推荐开发顺序

1. 建立 Workspace 与文档表结构及服务
2. 打通文档上传、解析、切分、向量入库
3. 打通默认问答接口
4. 增加摘要 / 追问 / 测验三个辅助任务
5. 补齐前端检索过程展示
6. 为后续多路召回/重排预留扩展点

## 13. 面试表达价值

这条链路适合这样表达：

1. 我把知识问答收敛成 `Document Knowledge Workspace`，避免做成泛聊天
2. 默认主路径是文档问答，摘要/追问/测验是显式触发的辅助动作
3. 通过 Workspace + 文档 + chunk + 向量表形成一套完整知识空间模型
4. 第一版优先用单次 LLM + RAG 跑稳主链路，为后续多路召回、重排和检索过程可观测打基础
